# ADR-002: Modular monolith and multi-file Prisma schema

- Status: Accepted (default)
- Date: 2026-10-14

## Context
Blueprint: "start with a modular monolith: one structured NestJS API, one PostgreSQL database and a separate background worker". Master Spec: no microservices unless measured scale justifies. Multiple build agents work in parallel and need low merge conflict surface.

## Decision
- Deployables: `apps/web`, `apps/api`, `apps/worker` (+ optional `apps/mobile-companion` later). One PostgreSQL database.
- Domains (modules) map 1:1 to folders: `modules/<domain>` in api, `features/<domain>` in web, `jobs/<domain>` in worker, `prisma/schema/<domain>.prisma`, `docs/<domain>-*.md`. Domains: identity, crm, revenue, analytics, sop, people, cx, platform, ai.
- Prisma multi-file schema (`prismaSchemaFolder`), one file per domain: `identity`, `crm`, `revenue`, `people`, `cx`, `platform`, plus `base.prisma` (datasource/generator/enums shared).
- Module rules: public service interface per module; no cross-module repository access; cross-domain FKs are allowed in schema; back-relations appended to the owning model by small atomic edits.
- Registries (module registry, nav registry, worker job registry, permission catalogue) are single-slot-per-domain files so agents never edit others' slots.
- During parallel waves use `prisma db push` on private DBs; consolidated migrations are generated by the lead at wave end.

## Consequences
+ Simple deploy/debug; transactional consistency across domains (deal close = one transaction).
+ Clear ownership and low conflict.
- Need discipline to avoid a big ball of mud: enforce with dependency-cruiser/ESLint import boundaries (Phase 1 CI).
- Scale-out later: split worker first (already separate); extract analytics read-model if needed (measure first).

## Alternatives rejected
Microservices (premature, operational cost on shared VPS); single schema.prisma (merge conflicts, contradicts Blueprint-only "prisma/schema.prisma" structure which predates Prisma multi-file stability).
