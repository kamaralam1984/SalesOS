## 2. Cross-area semantics (binding)

1. **Day-close materialisation (area A).** A nightly job (worker, idempotent) closes every past day for every active employee from `employee_profiles.joinDate` (or `users.createdAt` if no profile) : if no `attendance_records` row exists it writes `HOLIDAY` / `WEEKLY_OFF` (calendar), `ON_LEAVE` or `UNPAID_LEAVE` (an APPROVED leave request covering the day; paid vs unpaid from the leave type), else `ABSENT` when `attendance.autoMarkAbsent` (source `SYSTEM`). It never overwrites an existing record. Half-day approved leave on a day with a record leaves the record and is counted by readers through `leave_requests`. Payroll and the Earned Leave engine read `attendance_records` only for CLOSED days (day < today in the business timezone).
2. **Earned Leave (area A).** Daily per-employee engine in `@salesos/workforce-core` (pure `evaluateDay` + a Prisma-transaction runner shared by API and worker). For each closed day after `processedThrough` (and on/after the joining date when `countFromJoiningDate`) the status maps through `earnedLeave.treatment` to COUNT (1) / HALF (0.5) / SKIP (0). When the counter reaches `requiredEligibleDays` it writes ONE `leave_balance_txns` row (`kind=CREDIT_EARNED`, `amount=creditDays`, `balanceBefore/After`, `periodStart/End`, `eligibleDays`, `calculation` = the per-day outcomes, `policyVersion`, `createdById=null`, `uniqueKey = "EL:<userId>:<n>"` where n = credits already given + 1) and carries the remainder (counter - required) to the next period. A duplicate credit for the same period is impossible (unique key + one transaction + `processedThrough`). `maxBalance` caps the credit. Year-end carry-forward per policy writes `EXPIRY` rows. Every balance change (credit, debit, reversal, adjustment) is a `leave_balance_txns` row with a running balance; balances are always `SUM(amount)` per (user, type), never stored separately.
3. **Leave (area A).** Days = working days in [start, end] by the calendar, half day = 0.5 (single day only). Validate: dates, type active, overlap with another PENDING/APPROVED request (409), backdating limit, `maxConsecutiveDays`, balance (`needsBalance` types; shortfall = BLOCK or `unpaidDays` with explicit `confirmUnpaid: true` when `balanceExceeded = UNPAID_WITH_CONFIRMATION`). Approval chain from policy: steps MANAGER then HR (`leave_approval_steps`); a step is skipped (status SKIPPED) when the applicant has no manager; the approver cannot be the applicant; Founder may act at either step; reject at any step = REJECTED (terminal); both approve = APPROVED -> debit `DEBIT_LEAVE` txns (paid types, `days - unpaidDays`) in the same transaction; cancel before the leave starts reverses the debit (`REVERSAL`). Each transition: one function, one transaction, audit + outbox + notification.
4. **Goals (area B).** `Goal` = one cycle goal (default 45 days: `targetDate = startDate + cycleDays - 1`, editable). Status machine: ACTIVE -> PENDING_VERIFICATION (owner submits) -> COMPLETED (reviewer verifies) | back to ACTIVE (reviewer returns with note); ACTIVE/PENDING -> CANCELLED. `risk` (ON_TRACK/AT_RISK/COMPLETED/OVERDUE) is derived by a pure function in workforce-core from progress %, elapsed share of the cycle, `goals.atRiskGapPct`, today and status, stored on the row and recomputed on every update and by a daily worker job. Progress: `currentValue/targetValue` when a measurable target exists else a manual `progressPct`; milestones and linked work tasks are shown, but only the owner's progress update changes progress. Reviewer defaults to the owner's manager (else Team Lead/Founder); the reviewer can never be the owner. `goals.requireVerification=false` lets the owner complete directly.
5. **Work tasks (area B).** Lifecycle ASSIGNED -> ACCEPTED -> IN_PROGRESS -> REVIEW -> COMPLETED (assignee moves up to REVIEW; the assigner completes; `tasks.requireReview=false` lets the assignee complete directly); REJECTED (assignee declines with reason; assigner may reassign) and CANCELLED (assigner). Overdue is computed (open and `dueAt < now`), never stored. Scope for assigning: `own` = yourself only, `team` = visible users (`access.visibleUsers`), `org` = anyone active in the organisation. Append-only `work_task_events` for every change/comment/evidence.
6. **Payroll (area C).** Register only: no statutory deductions are computed (HR/Finance add PF/ESI/PT/TDS as manual DEDUCTION components or adjustment lines). Month `YYYY-MM`. Employed working days = calendar working days within [max(joinDate, monthStart), min(exitDate, monthEnd)]; `monthWorkingDays` = working days of the full month. Loss of pay = count(UNPAID_LEAVE) + (absentIsLossOfPay ? count(ABSENT) : 0) + halfDayLossOfPay x count(HALF_DAY), on closed days; paid days = employed working days - LOP; each component amount x paidDays / monthWorkingDays (Decimal, half-up 2 dp); net = gross earnings - deductions + adjustments. The payslip stores the facts used (`basis`). Run status: DRAFT -> CALCULATED (recalculable) -> APPROVED (Founder, `payroll:run:approve`; the preparer cannot approve their own run) -> PAID (Finance records an external payout reference; SalesOS never moves money); send-back APPROVED/CALCULATED -> DRAFT with reason; CANCELLED before PAID. A month cannot be calculated until it has ended and its days are closed (otherwise 409 `MONTH_NOT_CLOSED` listing the missing days). Employees see their own payslip only after the run is APPROVED. Money is never in logs/audit metadata/notifications.
7. **Directory, 360, org chart (area D1).** Directory data = name, employee code, designation (`employee_profiles.positionTitle`), department, manager, status (active/probation/exited), no contact data beyond work email. Employee 360 composes sections each guarded by the viewer's own permission and scope (profile/HR via `hr:records:view`, goals/tasks/attendance/leave/probation/performance via their keys); a section the viewer may not see is returned as `{ available: false }`. The org chart is built from `users.managerId` (Boss -> Managers -> members), cards with name/designation/department/status (no photo storage exists: show initials; document it), views organisation / department / team.
8. **HR automation (area D2).** Probation end = `joinDate + probationMonths` (default `hr.probationDefaultMonths`) using `addMonths`; decisions CONFIRM / EXTEND (months) / MARK_FOR_REVIEW with history (extend the existing people probation data or add rows through the existing `people` services; do not duplicate `probation_reviews`); reminders `hr.probationReminderDays` before the end to HR and the line manager; birthdays: `dateOfBirth` is HR data (`hr:records:*`), upcoming list for HR/Founder (`birthdays:view`), a team-visible list only for people with `shareBirthday=true` and only day+month; reminders `hr.birthdayReminderDays`; announcements CRUD + notification; HR hub; policy UI for `workforce_settings`; reports + exports (CSV/XLSX, audited, bounded) for attendance, leave, Earned Leave transactions, tasks, goals, holidays, probation, birthdays, department/manager performance.
